# ARGprep code review — 2026-08-09

**Scope:** correctness, documentation, efficiency, and deliberate simplification  
**Branch / HEAD:** `direct_maf` @ `60221fd`  
**Tests:** `77 passed in 25.61s` in the `argprep` conda environment  
**Repository changes:** this report only; no code, configuration, or existing data files were modified

## Executive summary

The core MAF-to-sites algorithm is reasonably disciplined for chromosome-scale data. The mmap-backed per-sample call arrays, chunked NumPy classification, streaming MAF parsing, and per-contig Snakemake jobs are complexity worth keeping. Most of the large performance problems found in the July review have been fixed.

There is one confirmed workflow correctness bug: `allow_multiallelic_snps: false` is ignored. Beyond that, the largest opportunity is not another micro-optimization. It is reducing the amount of output and reporting machinery. ARGprep writes a potentially enormous all-sites VCF and then scans it again to build an 881-line custom HTML report. If invariant genotypes are not a required product, removing or making that path optional would save substantial disk I/O, runtime, and code.

My preferred simplification direction is:

1. Fix the multiallelic flag propagation and test the false-config workflow.
2. Decide whether `all_sites.vcf` is a required scientific deliverable. If not, make it optional or remove it, and emit compact window/sample counters while calls are already in memory.
3. Reduce compatibility behavior: require exact contig names by default, with normalization as an explicit opt-in if it is genuinely needed.
4. Delete narrow helpers and rare-input support that do not justify their maintenance cost.

## Findings by priority

### High — `allow_multiallelic_snps: false` has no effect in the workflow

**Evidence:** `Snakefile:388` stores the configured Boolean. At `Snakefile:412-414`, the shell command adds `--allow-multiallelic-snps` only when it is true. The false branch adds nothing. However, `scripts/maf_to_sites.py:151-152` defaults `allow_multiallelic_snps` to true; disabling it requires the separate `--mask-multiallelic-snps` flag. Therefore both YAML values produce the default allow behavior.

The CLI masking path itself is tested (`tests/test_maf_to_sites.py:317`), but no workflow test sets the config to false, so the integration bug is invisible to the green suite.

**Recommendation:** pass exactly one of the two CLI flags, or simplify the script to a single `--allow-multiallelic-snps true|false` argument. Add one workflow-level false-config test.

### High — the all-sites VCF dominates avoidable I/O and reporting complexity

**Evidence:** `scripts/maf_to_sites.py:638-763` formats and writes every retained reference position to `combined.<contig>.all_sites.vcf`, including invariant sites. `scripts/summary_report.py:493-508` then reads every record again and loops over every sample genotype to derive window and per-sample counts. At chromosome scale this can mean writing and rereading hundreds of millions or billions of tab-delimited genotype cells.

The variant VCF, global mask BED, per-sample missing BEDs, and site-summary TSV already capture most downstream needs. The all-sites file is also what forces `summary_report.py` to carry a VCF parser and extensive aggregation state.

**Recommendation:** first ask one scientific/product question: do downstream users truly consume invariant genotypes? If no, remove `all_sites.vcf`. If sometimes, make it opt-in and default it off. While `maf_to_sites.py` already has the NumPy block in memory, emit compact per-window invariant/variant counts and per-sample called/variant totals. The report can then read small TSVs rather than a huge VCF.

This is the best combined speed-and-simplicity win in the repository.

### Medium — contig normalization is useful but disproportionately complex

**Evidence:** normalization and its defensive behavior span `scripts/common.py:31-47`, `Snakefile:133-230`, and `scripts/split_maf_by_contig.py:35-50`, with caches, intersections, exact-name preference, prefix stripping, ambiguity detection, remapping, dropping, and logging. Tests cover aliases such as `chr01`, assembly prefixes, ambiguous normalized contigs, and cross-file aliases.

This machinery protects against inconsistent input naming rather than performing core ARG preparation. It also creates surprising behavior: configured unmatched contigs are silently dropped as long as one contig remains (`README.md:75-76`). A typo can therefore produce a partial run instead of a hard failure.

**Recommendation:** require exact reference/MAF contig names by default. If real datasets routinely need aliases, keep normalization behind an explicit `normalize_contigs: true` compatibility option. For explicitly configured contigs, prefer failing on any unmatched name rather than silently producing a partial dataset. This would remove a meaningful amount of branching and reduce scientific ambiguity.

### Medium — the HTML report is doing too much work in one module

**Evidence:** `scripts/summary_report.py` is 881 lines and implements file parsing, aggregation, policy thresholds, HTML templating, CSS, and two handwritten SVG chart engines. `read_all_sites_stats` returns six structures. One of them, `per_sample_missing_retained_by_contig`, is populated at `scripts/summary_report.py:490,505-506` but never used afterward.

**Recommendation:** if the all-sites redesign above is accepted, make the report a simple renderer of precomputed TSV summaries. Drop the unused retained-site missing counters now. Consider whether per-contig plots and per-sample tables are both needed; each retained feature should have an identified consumer. Avoid introducing a framework—the simplest endpoint is a smaller, still self-contained HTML writer.

### Medium — stale ARGweaver cleanup is workflow side-effect complexity

**Evidence:** optional output changes the `direct_maf_sites` rule shape (`Snakefile:368-372`), adds a no-op dependency to the summary rule (`Snakefile:436-440`), and makes `summary_report` delete stale `.sites` files (`Snakefile:451-460`). Cleanup is unrelated to report generation.

**Recommendation:** pick a simpler contract. Either always generate the small `.sites` output, or leave stale optional outputs alone and document that changing output-mode configuration requires a clean target directory. The current design adds DAG and shell complexity solely to protect users who toggle a flag in place.

### Low — zero-length contig support is a clear candidate for deletion

**Evidence:** `scripts/maf_to_sites.py:498-557` contains a 60-line alternate output writer, invoked at lines 589-598, solely because a zero-length contig cannot follow the mmap path. It has dedicated tests for VCF and ARGweaver output. Real indexed biological references should not contain useful zero-length contigs.

**Recommendation:** reject zero-length contigs with a clear error. This intentionally sacrifices an implausible edge case and deletes a large duplicate output path plus its tests. A 1 bp contig already works through the normal algorithm and does not need special handling.

### Low — tolerant parsers hide bad inputs without simplifying the happy path

**Evidence:** `scripts/common.py:50-58` and `89-94` turn file-open errors into empty contig collections. `load_quality_mask` silently skips malformed BED rows (`scripts/maf_to_sites.py:101-114`). `iter_maf_blocks` ignores malformed/non-`s` rows and uses `zip` without verifying equal alignment-string lengths (`scripts/maf_to_sites.py:277-307,365`). Summary readers similarly skip malformed or unknown records.

These defenses do not provide strong correctness; they convert malformed data into missing data, skipped contigs, or partial summaries.

**Recommendation:** simplify toward fail-fast parsing for files ARGprep itself requires. At minimum, stop swallowing `OSError`, require equal MAF alignment-string lengths, and raise on malformed quality rows after comments/header lines are excluded. Clear failure is safer scientifically and often less code than permissive recovery.

### Low — dead and niche code can be removed

- `scripts/common.py:50` `read_fasta_contigs`, `:110` `extract_end`, and `:114` `extract_dp` have no callers.
- `scripts/simulate_msprime_indels.py:286` `apply_indel_events` is used only by its unit test, not by the simulation CLI. Delete it and its test unless it is a supported library API.
- `scripts/chr1_variable_plot.py` parses generated HTML/SVG back into data and assumes chromosome-specific element IDs and chart geometry. It exists to compensate for a plotting choice in the main report. Fix the main plot scale or drop this helper.
- `scripts/window_to_fasta.py` is a plausible utility, but it is not in the workflow and depends on the expensive all-sites artifact. Retain it only if there is a known user; otherwise it should not determine the core output architecture.

### Low — documentation and example configuration disagree on CPU use

`README.md:54` documents `maf_threads: 1`, and the Snakefile notes that `maf_to_sites.py` is single-threaded. `example_data/options.yaml:23` nevertheless requests `maf_threads: 2`. That reserves an unused core and teaches the wrong setting.

**Recommendation:** change the example to 1. More strongly, remove `maf_threads` until the program actually uses multiple threads; a configurable knob that cannot improve performance is misleading.

## Complexity worth keeping

Not all defensive or advanced-looking code is over-engineering:

- **mmap-backed per-sample calls and chunked NumPy classification** (`scripts/maf_to_sites.py:599-687`) bound resident memory and accelerate the true `samples × contig length` workload. Keep this unless measurements on production chromosomes show a simpler in-memory array fits comfortably.
- **Per-contig MAF splitting** avoids rescanning every whole-genome MAF once per contig. Compressed chunks trade temporary disk for substantially less repeated decompression/parsing and are reasonable for large inputs.
- **The final coverage invariant** (`scripts/maf_to_sites.py:769-772`) is only four lines and guards a scientifically important partition of retained versus masked bases. Keep it.
- **Exact missingness and quality-mask semantics** are core scientific policy, not merely defensive programming. Simplify their interface if desired, but retain explicit behavior and focused tests.
- **No-sample failure** is cheap and prevents meaningless output. Unlike zero-length-contig output support, the guard itself adds negligible complexity.

## Documentation gaps

1. The README says multiallelic sites can be disabled, but the workflow currently cannot honor that setting. Fix code and add an integration example/test; do not merely revise the docs.
2. Document that malformed BED/MAF records are currently skipped and decide whether that is intended. Silent recovery has scientific consequences.
3. State whether the all-sites VCF is a supported downstream product or an internal reporting artifact. This decision controls the largest simplification opportunity.
4. Correct the `maf_threads` example or remove the option.
5. The README’s normalization section is thorough, but it should warn more prominently that unmatched requested contigs may be skipped and a partial run may succeed.

## Suggested iterative plan

### Phase 1 — correctness, minimal risk

- Fix false multiallelic config propagation.
- Add one workflow regression test.
- Remove the unused summary aggregation and dead common helpers.
- Align `maf_threads` documentation/example with actual single-threaded behavior.

Expected outcome: no intended behavior change except making the documented false setting work.

### Phase 2 — agree on the product boundary

Answer these before editing code:

1. Is `all_sites.vcf` consumed downstream, or only by ARGprep reporting/helpers?
2. Are automatic contig aliases required by current production datasets?
3. Does anyone use the chromosome-1 plot and window-to-FASTA helpers?
4. Is toggling `emit_argweaver_sites` in the same results directory a workflow that must clean itself up?

These answers determine which complexity is real product behavior versus historical accommodation.

### Phase 3 — high-impact simplification

- Default all-sites emission off or remove it; emit compact report counters during calling.
- Reduce `summary_report.py` to rendering precomputed summaries.
- Require exact contig names by default; make alias normalization opt-in or remove it.
- Reject zero-length contigs rather than supporting duplicate output logic.
- Delete unused/niche helpers that have no identified users.

### Phase 4 — fail-fast input policy

- Stop swallowing required-file I/O errors.
- Validate MAF row shape/alignment lengths once per block.
- Choose strict versus permissive quality-BED parsing and document the choice.
- Keep tests centered on realistic biological inputs and core scientific invariants, rather than expanding the unlikely-edge-case matrix.

## Test assessment

The suite is strong for its size: 77 tests cover the main caller, workflow integration, zero-length behavior, normalized names, gzip chunks, strand-aware quality masking, multiallelic CLI behavior, ARGweaver output, and report rendering. The main gap is configuration propagation: unit tests prove that CLI switches work, but do not systematically prove that YAML false values reach those switches.

Rather than adding tests for more exotic inputs, add a compact parameterized workflow test covering each Boolean config in both states. Then delete tests alongside any intentionally removed edge-case features. Test count is not a goal; confidence in the supported behavior is.

## Final recommendation

Fix the multiallelic workflow bug first. Then prioritize a product decision about the all-sites VCF. If it is not essential downstream, removing/defaulting-off that artifact and precomputing report counters is likely to deliver the largest speedup, disk reduction, and code simplification simultaneously. After that, exact contig naming and rejection of zero-length references are sensible places to trade unlikely-input protection for a smaller, clearer system.
